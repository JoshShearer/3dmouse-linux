## Why `buttons_verified` and not higher

The axes and both buttons were checked on real hardware, through both input paths (evdev and
hidraw) and through all three outputs this project produces:
- the libspnav socket
- the Blender NDOF client
- desktop emulation via uinput

`outputs_verified` and `full_verified` are reserved for device-side outputs, such as LED or LCD
output reports, and for the other transports. The Compact exposes no documented host-controllable
output, and SRS §4.4 forbids sending speculative HID output reports. So this record stops at
`buttons_verified`. Only this vid/pid on USB is covered. No other Compact revision and no wireless
SpaceMouse is covered.

## Results

### Device identity and access
- The kernel binds `hid-generic` and exposes `hidraw0` plus one evdev node (`event27`).
- The report descriptor is captured in `tests/fixtures/descriptors/256f-c635-usb.hex`.
- The udev rule `70-3dmouse-linux.rules`:
  - grants a `uaccess` ACL on hidraw to the seat user (`crw-rw----+`)
  - sets `LIBINPUT_IGNORE_DEVICE=1`, so the compositor doesn't also treat the device as a pointer.

`tests/fixtures/spnav/256f-c635-hidraw-installed.jsonl` (installed service on hidraw, read with

| push right | +TX |

- 0 malformed reports were seen in either capture.

### Native application: Blender 4.5.15
Blender connected to `/run/spnav.sock`. Pan, zoom, orbit and twist all navigated the 3D viewport
correctly. The tester also changed per-axis inversion in the Blender profile through the GUI and
confirmed that Blender followed the change.

### Desktop emulation (scroll)
The `desktop` profile was active. Each segment was summed between button markers.

| Push | Vertical scroll (WHEEL_HI_RES) | Horizontal scroll (HWHEEL_HI_RES) |
|---|---|---|
| right, about 2 s | −47 | **+2537** (scroll right) |
| forward, about 2 s | **−4514** (scroll down) | +72 |

Cross-axis leakage is about 2 %. The signs match evdev conventions.

### Native application: OpenSCAD 2021.01 (Arch `openscad`)
- **Initial report:** "not working". Diagnosis with an LD_PRELOAD `connect()`/`spnav_open()` logger:
  OpenSCAD never called `spnav_open()`. Its SpaceNav input driver is compiled in but is off unless
  `[input] enableDriverSPNAV=true` is set. Ticking the box in Preferences did not persist the key
  on this install.
- **With the key set:** OpenSCAD connected to `/var/run/spnav.sock`, `spnav_open()` returned 0,
  and the tester confirmed the view navigates.
- **Product change:** none needed in the driver. The OpenSCAD preset note (shown in the GUI) now
  gives both ways to enable it.

### Native application: KiCad 10.0.7 (Arch `kicad`)
- `pcbnew` links `libspnav.so.0` and connects to `/run/spnav.sock`.
- **Desktop emulation (the original preset):** works, but the user reported that scrolling "is not
  smooth". KiCad maps each wheel event to a discrete zoom or pan step.
- **Native 6-DOF:** after switching the profile and restarting pcbnew, the user reported "smooth
  now" on the PCB canvas and in the 3D viewer. The preset now ships as `native6dof`.
- **Restart behaviour:** libspnav clients don't reconnect after 3dmoused restarts. A pcbnew that
  was running during a package upgrade received nothing until it was restarted. spacenavd restarts
  behave the same way. This is documented in the install guides.
- **Stale-motion finding:** while pcbnew was unfocused, it stopped reading the socket, and its send
  queue grew to about 213 KB of queued motion. That would have replayed as a view jump on focus.
  Fix: `sm-spnav` now withholds non-neutral motion from a client whose unread backlog
  (`SIOCOUTQ` plus our buffer) exceeds 16 KiB. Neutral frames and buttons are always delivered.
  This is covered by the unit test `idle_client_backlog_is_bounded_and_ends_neutral`.

### Screen lock (SRS §4.6 rule 4)
- **First run found a defect.** Omarchy's Quickshell lock holds an ext-session-lock in-process. It
  runs no known locker binary and never sets logind `LockedHint`, so the agent didn't see the lock.
  About 3000 hi-res scroll units were injected while the screen was locked.
- **Fix.** On Hyprland the agent now also checks `j/monitors`. Hyprland lists `LOCK` in
  `solitaryBlockedBy` while any session lock is held. The check is in
  `sm_desktop::lock::hyprland_session_locked` and has a unit test. The lock poll is now 1 s.
- **Re-test.** The lock was detected 0.65 s after the locker reported `session-locked=true`, and the
  unlock 0.35 s after. The virtual device emitted **0 events** during the run, including the locked
  window, while the tester pushed the cap and pressed a button.
- **Residual risk.** For up to the poll interval (≤ 1 s) after a lock starts, injection is still
  possible. While the lock is held the compositor only routes input to the lock surface. This is
  recorded in the risk register.

### Pop!_OS 24.04 LTS (Ubuntu base), bare metal, 2026-11-10
- Host: Pop!_OS 24.04 LTS, kernel 7.2.6, GNOME Shell 46.0, **X11 session**. The Compact was on USB
  (`lsusb`: `256f:c635`). spacenavd 1.2 was installed but inactive.
- Install: `sudo apt install ./3dmouse-linux_0.1.0-1~ubuntu24.04_amd64.deb`, then log out and in.
  No manual permission edits. `3dmoused` (system) and `3dmouse-agent` and `3dmouse-osd`
  (user) came up active.
- `3dmousectl diagnostics`: every check OK.
  - udev rules installed; `/dev/hidraw0` readable by the user
  - broker in native-owner mode, `/run/spnav.sock` present
  - uinput injection available
  - device stream `ready via hidraw`: 1652 frames, 0 malformed, 0 watchdog resets
  - focus tracking `x11` (`_NET_ACTIVE_WINDOW`), and the focused Brave window was reported
  - overlay connected
- libspnav: the distro's libspnav, through a probe client, connected with protocol 1 and got
  `3Dconnexion SpaceMouse Compact`, 6 axes, 2 buttons. `status` listed the client.
- Overlay, X11 fallback window (`3dmouse-osd: X11 overlay`): the "Sensitivity reset" toast
  showed at the bottom centre, and the radial ring with four labelled slices showed in the
  centre of the primary monitor until release. Both were captured with `ffmpeg -f x11grab`.
- Hands-on with the Compact (tester at the machine, 2026-11-10):
  - `3dmousectl monitor --duration 90s` while the tester moved one axis at a time: every axis
    reached both ends. TX −320…348, TY ±350, TZ −299…350, RX −350…234, RY ±350, RZ ±350. Button 0

  - `3dmouse-config`, maximised at 2580 px: the Profiles editor was squeezed off-screen

    Fixed in two steps: the list width now scales, the editor reflows with a vertical scrollbar,
    and it was re-rendered at 760 to 2580 px. After `apt install --reinstall` (20:03) the tester
    confirmed it on Pop!_OS, both maximised and narrow.
  - The same reinstall brought the SIGHUP fix (the agent stays active after SIGHUP) and the
    `web-browsers` preset. Diagnostics: 9 OK.
  - Lock (SRS §4.6 rule 4), with the `desktop` profile active in Brave: Super+L. The agent logged
