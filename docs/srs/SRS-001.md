# 3DMouse Linux — Product Requirements, Architecture, and Claude Code Execution Specification

**Document:** SRS-001  
**Revision:** 1.0 — 2026-11-10  
**Status:** Implementation-ready baseline; hardware-specific compatibility remains to be validated  
**Project name:** 3DMouse Linux (`3dmouse-linux`). The working name in early drafts was "SpaceMouse Linux"; it was renamed before the first public release to keep the 3Dconnexion trademark out of the project name.  
**Primary development target:** Pop!_OS 22.04 / Ubuntu-family Linux, x86_64, X11 and Wayland as available  
**Other target platforms:** Ubuntu 24.04 LTS+, Debian 12/13, Fedora current supported, Arch/Manjaro, openSUSE; ARM64 where feasible  
**License:** Select before implementation after auditing dependencies; GPL-3.0-or-later is a practical option if incorporating GPL components, but process isolation and license obligations require review.

---

## 0. Executive mandate

Build, package, document, and test a reliable open-source Linux driver and management suite for the 3Dconnexion SpaceMouse family. It must target **feature parity or superiority to the Windows 3DxWare experience**, not merely basic 6-DOF navigation. Support modern and legacy wired and wireless devices; six-axis motion; all available model-specific buttons; programmable commands; per-application profiles; advanced calibration; device diagnostics; and, where protocols are validated, indicators, batteries, wireless pairing, LCD/key labels, and other model-specific capabilities.

**Non-negotiable outcomes:**

1. A normal user can install and uninstall cleanly through a signed or verifiable distribution package, without editing udev rules or executing mysterious commands.
2. Supported plugged-in devices work immediately for supported integration paths, survive reboot, reconnect after hotplug and sleep/resume, and never create duplicate input events.
3. Native applications which already work with spacenavd/libspnav must continue to work; do not steal their device or interrupt their event path.
4. Mapping, speed, axis transformations, modes, buttons, macros, profiles, and diagnostics are configurable through an accessible GUI.
5. On-screen overlays, shortcut injection and per-app switching work on desktops where the compositor and security model permit them, and limitations are conspicuously disclosed.
6. Every hardware compatibility claim is backed by a measured test. Untested and partial support must be honestly labeled.
7. The product starts automatically, logs clearly, fails safely, and is upgradeable without losing settings.

**Important conceptual boundary:** Most Linux USB HID devices do not need a new kernel module. Investigate a user-space daemon built on the Linux HID/evdev/hidraw stack, with optional integration into an existing spacenavd instance. Only propose kernel code if measured evidence shows that user-space solutions are insufficient.

## 1. Mandatory research and verification phase

Do not start coding until completing an evidence-based technical reconnaissance, summarized in `docs/research/` with URLs, dates, license details, known gaps, and applicability:

- Official 3Dconnexion hardware catalogue, product manuals, Windows 3DxWare documentation/release notes, Linux support matrix, 3Dconnexion SDK/app integration documentation, support lifecycle; establish exact current product IDs and revision distinctions.
- FreeSpacenav/spacenavd, FreeSpacenav/libspnav, FreeSpacenav/spnavcfg: APIs, service ownership, supported IDs, HID mappings, licensing, X11 fallback and native AF_UNIX protocol, releases and known defects.
- SpaceUX and older SpaceMouse_3dconnexion Linux control project; identify reusable ideas and incompatible assumptions; do not equate their claims with production-level coverage.
- Linux HID and evdev, libudev, hidraw, BlueZ Bluetooth LE/Classic device discovery, uinput, systemd/logind, Polkit, XDG Desktop Portal, libei/liboeffis, X11/XInput2/XTest, desktop/window-manager-specific facilities.
- Real application paths: FreeCAD, Blender, KiCad, OpenSCAD, PrusaSlicer, Onshape (browser), CAD applications with Linux versions and professional plugins. Verify integration individually and distinguish application-native 6-DOF support from translated keyboard/mouse input.
- Existing HID product ID mappings. Do **not** assume a single vendor ID or deduce USB/Bluetooth product IDs from model names. Maintain per-transport and per-revision records.
- Software composition analysis and license compatibility. Do not copy proprietary Windows binary code or assets. Respect trademark and API rights; document reverse engineering and source provenance.

Deliver `docs/research/landscape.md`, `hardware-inventory.md`, `windows-feature-matrix.md`, `linux-compatibility-matrix.md`, `architecture-decisions/`, and a risk register.

## 2. Product success criteria and scope

### 2.1 Release stages

- **P0 / Foundational:** Well-behaved 6-DOF device read path; wired SpaceNavigator/Compact/Pro as tested; native spacenav interoperability; safety and diagnostics; X11 basic interface; Ubuntu/Pop!_OS package; configurable per-axis controls; button binding; easy rollback.
- **P1 / Full desktop utility:** Application profiles, automatic switching, robust Bluetooth/receiver transports for tested devices, advanced mappings, OSD, macros, UI wizard, Wayland permissions/backends, multiple device management.
- **P2 / High-end model parity:** Enterprise LCD/buttons, Pro wireless variant capabilities, custom command screens, device indicators and battery, community profile importer, productivity extensions.
- **P3 / Ecosystem:** Optional plugin API, native CAD application plugins, cross-distro packaging, stable SDK and developer docs.

Never treat deferred model-specific hardware controls as completed P0 features. Full-family support is the overall program goal, not a claim for the first alpha.

### 2.2 Hardware coverage

Create a versioned hardware registry with each **exact** VID/PID, bus/transport, HID interfaces, report descriptors, firmware variants, axis mapping, button mapping, outputs, pairing behavior, and test evidence. Minimum device families to investigate:

| Family | Physical variations / requirements | Test level before fully supported |
|---|---|---|
| SpaceMouse Enterprise | 6 axes, multiple buttons, LCD/application command labeling, QuickView and mode keys | Actual hardware axis + each key + output display tests |
| SpaceMouse Pro Wireless | New Bluetooth edition and prior USB receiver / cabled variants | Physical test on each transport and hardware revision |
| SpaceMouse Pro | Wired and legacy revisions | Physical test on all input controls |
| SpaceMouse Wireless | Bluetooth edition, earlier receiver and wired operation if supported | Physical tests for every supported transport |
| SpaceMouse Compact | Wired and historical hardware revisions | Physical test |
| SpaceNavigator / SpaceNavigator for Notebooks | Legacy USB | Physical test |
| SpaceExplorer, SpacePilot, SpacePilot Pro, SpaceTraveler, SpaceMouse Plus, CadMan, SpaceBall series | Legacy USB and/or serial where applicable | Explicit verified/partial/unsupported designation |
| Future/unknown SpaceMouse-compatible HID | Safe generic descriptor-based motion discovery where protocol supports it | Generic support only, no fabricated buttons/output capabilities |

3Dconnexion **CadMouse, Keyboard, Numpad** are separate device categories and must **not** be falsely recognized as 6-DOF SpaceMouse devices. Optionally design a later input-product plugin architecture, but never intercept ordinary keyboards/mice accidentally.

Per device record: `unknown`, `detected`, `axis_verified`, `buttons_verified`, `outputs_verified`, `full_verified`, `partial`, `blocked`. Provide exact test fixture date and evidence. Do not claim full device-family support based on another revision or protocol transport. Explicitly provide friendly fallback for unknown hardware.

### 2.3 Operating environment

- Pop!_OS 22.04 (priority test), Ubuntu 24.04+, Debian stable, Fedora, Arch, openSUSE.
- X11; KDE Plasma Wayland; GNOME Wayland; COSMIC Wayland; wlroots compositors as separate target matrices.
- x86_64 baseline, ARM64 secondary; systemd baseline; rootless normal UI sessions.
- USB hotplug, receiver devices, Bluetooth Classic/LE when applicable, suspend/resume, session lock/unlock, multiple seats, unplug during operation, user switching, concurrent applications.
- Support Flatpak/Snap application contexts only where input access and application integration are architecturally viable; avoid claiming host injection bypasses sandbox constraints.

## 3. Functional requirements (FR)

### FR-100 — Discovery and ownership

- FR-101 Enumerate candidate devices via udev/logind and transport-specific discovery, tracking stable device identities per physical peripheral; differentiate receiver from the device when possible.
- FR-102 Probe safely without interrupting unrelated USB HID consumers.
- FR-103 Read multiple HID collections/interfaces when required; associate controls belonging to one physical device.
- FR-104 Support reconnect without restart; handle disconnect during button hold or motion by releasing synthetic states and zeroing the navigation stream.
- FR-105 Support multiple simultaneously connected SpaceMouse devices with independent profiles and attribution, even though legacy libspnav event protocols do not distinguish devices; clearly specify compatibility aggregation policy.
- FR-106 Expose health, connectivity, firmware where available, serial/identifier with privacy-conscious display and logs.
- FR-107 Detect another manager such as spacenavd and choose one safe ownership strategy. Never compete for exclusive EVIOCGRAB/hidraw or double-inject events. Provide selectable supported modes: `integrated-spacenav`, `native-owner`, and `passive-monitor` with verified semantics.
- FR-108 Ship controlled udev rules; prefer `uaccess`/logind; minimal group/device privileges; avoid chmod 0666 and blanket vendor-ID grants.
- FR-109 A model adapter cannot execute privileged commands or issue arbitrary HID output reports without explicit allowlist and validation.

### FR-200 — Six-axis signal pipeline

- FR-201 Read TX, TY, TZ, RX, RY, RZ at native available event cadence, with correct signedness, endian handling, report length, neutral state, and per-model scale.
- FR-202 Expose canonical normalized floating-point axes in [-1, 1], plus raw values for diagnostics. Avoid incorrectly assuming raw ranges are identical for every axis/model.
- FR-203 Per-axis gain, inverse direction, axis swap/remap, deadzone, asymmetric deadzone if necessary, saturating clamp, translation and rotation global scales.
- FR-204 Linear, exponential/power, optional S-curve response curves; show exact mathematical behavior and live preview.
- FR-205 Optional smoothing filter with adjustable time constant, latency budget and no drifting; expose interpolation versus polling behavior.
- FR-206 Dominant-axis modes, translation-only, rotation-only, axis lock, intelligent view mode, per-app control settings.
- FR-207 Optional recalibration/center baseline only where supported; never write dangerous undocumented device calibration data.
- FR-208 Input reset on inactivity/disconnect, jitter rejection, no indefinite movement from last nonzero frame.
- FR-209 Frame transformations must be documented; user-facing invert/left-right directions tested in representative 3D scenes.
- FR-210 Maintain an identical axis pipeline across all output backends unless the app requests a bypass. Prevent double application of sensitivity through both daemon and application.

Suggested canonical pipeline: `physical report -> validated device decoder -> timestamped raw vector -> calibration -> device-space mapping -> per-profile transform -> deadzone -> response curve -> filter -> mode constraints -> normalized event -> output broker`.

### FR-300 — Buttons and command engine

- FR-301 Enumerate every **verified** physical button, with device-specific labels and a visual device illustration or generic grid; identify duplicate HID reports by physical control.
- FR-302 Bind buttons to: native application action, key/key chord, mouse button, wheel/scroll, custom shortcut, system/media command, workspace/window action, application launch, radial menu, view presets, toggles, profile switch, and no-op.
- FR-303 Short press/long press/double press/chords only when ambiguity is resolved with explicit priority/timing rules; do not interfere with held modifier keys.
- FR-304 Macro editor with sequential actions, delays, optional limited conditional profile predicates; include cancellation and recursion protection.
- FR-305 Restrict shell execution to explicitly user-created actions with confirmation; never execute arbitrary profile imports automatically; macros should be declarative by default.
- FR-306 Send synthetic key-up on crash, unplug, profile switch, desktop lock, and timeout to avoid stuck modifiers.
- FR-307 QuickView presets for top/bottom/left/right/front/back/isometric, fit, rotation lock, and user views when the target app implements the command; do not pretend one generic keyboard shortcut universally achieves this.
- FR-308 Context-aware help and current button assignments in an OSD.

### FR-400 — Application-aware behavior

- FR-401 Auto-select active application/workspace profile on focused-window identity, with secure desktop-specific identity providers and graceful fallback.
- FR-402 Profiles by executable/desktop-file identity, Flatpak app ID, window class, optional title regex (explicit user opt-in); distinguish app-wide and document/workspace overrides.
- FR-403 Default -> device -> app -> user override precedence, deterministic and documented; optional application/workspace subprofile layer.
- FR-404 Atomic profile switching and conflict-free output. No lost event stream or double injections when switching.
- FR-405 Ship audited presets for Blender, FreeCAD, KiCad, OpenSCAD, PrusaSlicer, and basic desktop navigation; only claim integration after app/version testing.
- FR-406 Export/import profiles as versioned JSON or TOML with schema validation, import preview, migration, and no arbitrary executable payloads.
- FR-407 Allow profile duplication, search, reset, backup, restore, cloud-free operation, and simple profile-sharing packages.
- FR-408 Provide integration modes: `native-6dof`, `application-plugin`, `desktop-emulation`, `none`, and explicit safe coexistence policy per app.
- FR-409 For web CAD (e.g. Onshape), evaluate an opt-in browser extension + localhost bridge; obtain user gesture/permission, validate origin, CSRF and message schemas, no unbounded localhost command interface. General mouse emulation is a fallback, not equivalent native 6-DOF integration.

### FR-500 — Desktop action/output backends

- FR-501 Native `spacenavd/libspnav` interoperability to preserve apps that already consume it. Test socket protocol and X11 compatibility independently; do not invent protocol versions or assume multi-device identifiers exist in legacy format.
- FR-502 For X11: focused-window detection, overlays, and input synthesis using available authorized APIs, with protection from feedback loops.
- FR-503 For Wayland: use compositor-sanctioned or portal-mediated interfaces, libei/liboeffis where supported, or explicitly permitted uinput backend. Do not assume XTest or XWayland will control native Wayland clients.
- FR-504 For Wayland overlays: implement Qt6 layer-shell where supported, and a GNOME-compatible fallback or no-overlay mode with accurate capability reporting. Avoid false claim of universal global overlay support.
- FR-505 For GNOME/COSMIC/KDE: record actual availability of active-app introspection and global shortcuts; use compositor-specific plugins only when robust, maintained and permitted.
- FR-506 Avoid stealing device focus or injecting input while screen is locked, unless explicitly designed and security-reviewed.
- FR-507 Desktop fallback modes: scroll, zoom, pan, window switch, workspace switch, media control, virtual joystick/game mode (opt-in), accessibility navigation (opt-in).
- FR-508 Support simultaneous native app movement and dedicated device buttons only under a tested shared ownership contract; ensure one entity is responsible for each action.

### FR-600 — Wireless and device outputs

- FR-601 Support all identified wired/receiver/Bluetooth transports using separate, test-backed protocol drivers.
- FR-602 Provide battery level/charging/connection quality only when firmware exposes reliable information; show 'unavailable' rather than invented data.
- FR-603 Use BlueZ for Bluetooth discovery/pairing where appropriate and rely on system pairing permission flows; do not implement a parallel Bluetooth stack.
- FR-604 Reconnect automatically after suspend, Bluetooth drop, receiver unplug/replug, or device power cycle; handle duplicate device identities.
- FR-605 Read/write LEDs/brightness/display commands only after collecting verified output report formats and conducting safe bounded tests; do not send speculative undocumented feature reports.
- FR-606 Enterprise LCD: discover resolution, color model, update rate, protocol, dimensions, display addressing, key-to-display association, and firmware behavior; dynamic app labels/icons, pagination, text clipping, brightness/power if verified; provide graceful fallback when unsupported.
- FR-607 Any firmware update support is **out of scope** unless an official, documented, verified safe mechanism exists. Do not attempt firmware modification or flashing to unlock features.

### FR-700 — Configuration GUI (Qt6/QML)

Provide a modern accessible UI, keyboard navigable, HIDPI-aware, dark/light/system themes, correctly labeled units and axes, undo/redo for unsaved edits, autosave or clear Save/Cancel semantics, localization-ready strings and responsive layout.

**Views:**
1. **Home dashboard:** installed version, service status, connected devices, connection type, active application/profile, warnings and one-click self-test.
2. **Device page:** selectable physical device, visual six-axis animation, live 3D cube, button grid, model/connection info, raw event inspector.
3. **Navigation page:** master speed; translation vs rotation speed; individual axes; deadzones; curves; dominant axis; reverse axes; smoothing; rotation lock; sensitivity preview; presets; reset.
4. **Buttons page:** physical button map, searchable command palette, bind/edit/clear actions, tap/hold/double, modifier conflict warnings.
5. **Application profiles page:** list/search apps, current focused app, auto-switch settings, global inheritance, import/export, per-application compatibility status.
6. **Macro/radial editor:** drag-and-drop command slots, nested menus within reasonable limits, command preview, test runner, safe macro DSL, conflict detection.
7. **OSD customization:** theme, placement, scaling, visibility/fade time, button hints, always-visible diagnostic overlay (optional).
8. **Wireless/device features:** pairing help, reconnect, batteries, LEDs, Enterprise LCD layout where supported.
9. **Diagnostics:** check udev, service, competing daemon, session type, backend authorization, input permissions, event rate, dropped/invalid events, per-axis trace, test output, optional recording/replay with redaction.
10. **Settings/system:** autostart, updates/channel, CLI integration, logging level, import/export backup, permissions, telemetry opt-in (default off), troubleshooting, about/licenses.

Use a descriptive UI wizard on first run: identify device, validate input, detect desktop, test native app integration, offer sensible presets, optionally request permissions, verify control success, and save settings. Never demand sudo from the GUI for ordinary tasks; elevated operations go through discrete package-manager/Polkit-sanctioned workflows.

### FR-800 — Installer and lifecycle

- FR-801 Build `.deb` first; `.rpm`, PKGBUILD/AUR or distro packages, optional AppImage for GUI only after host daemon integration is reliable. A Flatpak GUI may be offered with a separately installed host service; do not falsely claim that sandboxed app alone can manage HID devices and systemd services.
- FR-802 Provide clean install/upgrade/reinstall/downgrade/uninstall paths; explicit options to preserve or delete profiles.
- FR-803 Installer identifies packages/services (`spacenavd`, vendor legacy driver, other tools) and offers a safe, explained coexistence/migration plan. No silent disabling/removal of third-party packages.
- FR-804 Prefer OS-native service ownership: privileged minimal system service for protected hardware if necessary; unprivileged per-user session daemon for profiles/UI. Use systemd units with explicit dependencies, restart policy, security hardening, session-awareness and no network service exposure.
- FR-805 Deploy narrowly scoped udev rules and minimize permissions, handling `udevadm reload` and device replug cleanly. Document polkit authorization if needed.
- FR-806 Avoid arbitrary `curl | sudo bash`; distribute signed packages and publish checksums/provenance/SBOM. Reproducible builds where feasible.
- FR-807 Install desktop icon, menu launcher, optional status indicator compatible with DE capabilities, CLI and manpages. No desktop prompt at boot unless an actionable error occurs.
- FR-808 Support offline use, host-only data storage, no account or API keys required, no internet at runtime. Check for updates opt-in or clearly disclosed.
- FR-809 Settings in XDG config/data directories; use atomic write, versioned migration, safe backup, locked writes across sessions, never world-readable sensitive diagnostics.
- FR-810 Support service startup without an attached device, quick wake/reconnect, no blocking GUI on hardware.

### FR-900 — CLI and diagnostics

Command names are **proposed interfaces**, subject to ADR approval, with stable semantics and machine-readable JSON options:

```
3dmousectl status [--json]
3dmousectl devices list [--json]
3dmousectl devices inspect <device-id>
3dmousectl diagnostics check [--json]
3dmousectl diagnostics record --duration 10s --redact
3dmousectl diagnostics replay <fixture>
3dmousectl profile list
3dmousectl profile activate <profile-id>
3dmousectl profile import <file> --dry-run
3dmousectl profile export <profile-id> --output <file>
3dmousectl service health
3dmousectl support-bundle --redact --output <path>
3dmousectl version
```

Every command must display useful actionable failures, appropriate exit codes and optional JSON for automated support. Never include USB serial IDs, keyboard activity, application document names or proprietary material in shared bundles without explicit consent. Provide privacy preview/redaction.

## 4. Architecture

### 4.1 Recommended components

```
+--------------------------------------------------------------+
| Qt 6 / QML Management UI | CLI | Optional App/Browser Bridges |
+------------------------+-------------------------------------+
                         | versioned D-Bus / AF_UNIX API
+------------------------v-------------------------------------+
| User Session Service (non-root)                              |
| Profiles / Auto-Switch / Action Engine / GUI State / OSD     |
| App Adapters / Desktop Capability Registry / Macro Sandbox   |
+------------------------+-------------------------------------+
                         | authenticated, versioned IPC
+------------------------v-------------------------------------+
| Input Broker / Device Owner                                  |
| udev / libevdev / hidraw / BlueZ                              |
| Model Protocol Adapters | Axis DSP | Health and State         |
+-----------+-----------------------+--------------------------+
            |                       |
+-----------v-----------+ +---------v------------------------+
| Existing spacenavd /  | | libspnav-compatible event output |
| coexisting app path   | | native app / permitted emulation |
+-----------------------+ +----------------------------------+
```

**Critical design challenge:** Direct hardware ownership and existing `spacenavd` ownership are competing options. Implement exactly one authoritative hardware reader/owner for a device, selected through a deterministic negotiation strategy. The native-owner mode needs a compatibility server or another proven way to retain app support. The integrated-spacenav mode may use only data that the library exposes and should not claim per-device attribution if legacy protocol strips it. Record the final approach in an Architecture Decision Record supported by integration tests. **Do not** automatically layer an independent low-level reader over an exclusive spacenavd instance.

### 4.2 Suggested technology

- **Rust stable** for device registry, protocol codecs, input pipeline, state machine, IPC, profile storage, action engine, CLI and tests. Strong typing, strict memory safety, bounded queues and explicit errors.
- **Qt 6/QML** for GUI, native desktop integration, accessible controls, advanced graph widgets. Evaluate `cxx-qt`, C ABI, or narrow D-Bus boundary; prefer process boundary rather than fragile Rust/Qt direct integration unless justified.
- **systemd + udev + logind** for lifecycle, notifications, sessions and access. D-Bus for status/control with peer authentication; AF_UNIX for high-rate motion stream only if necessary.
- **libevdev / hidapi / native hidraw** evaluated per transport, with no assumption that simultaneous read access is harmless; BlueZ integration for Bluetooth.
- **SQLite or versioned TOML/JSON** for profiles, depending on concurrency and upgrade evidence; atomic migrations and schema validation mandatory.
- **No Electron/browser framework as a hard dependency**; can offer lightweight web management only if it does not create a security or resource burden.

### 4.3 Protocol rules

- Use typed envelopes: protocol version, event type, per-device ID, monotonic timestamp, axis data, button state, feature flags, sequence number, context, source.
- Negotiate API versions. Keep high-frequency motion transport separate from infrequent control changes when beneficial.
- Reject malformed/out-of-range events. Bound packet sizes, queue length, macro steps and recursion; ensure read/write timeouts.
- Use monotonic time for filters and long presses; reset time-dependent filters on suspend/resume.
- Set a conservative resource ceiling; avoid high CPU polling or busy loops. Debounce UI updates independently from input cadence.
- Use an explicit device state machine: `absent -> discovered -> probing -> ready -> suspended/disconnected -> reconnecting -> ready`, plus `error/unsupported`.
- No network listener by default. Any optional browser integration binds to localhost and uses origin validation, authorization tokens, CSRF protection, rate limits and deliberate enablement.

### 4.4 Device adapters

Each hardware adapter must expose: `probe`, `descriptor`, `decode_motion`, `decode_buttons`, `decode_status`, `supported_outputs`, `write_safe_output`, `transport_capabilities`, `on_disconnect`, and fixture tests. Device IDs and mappings come from a data registry, **not** sprawling hardcoded branches. A generic HID adapter is limited to positively identified axis usages. Treat unknown output reports as unsupported.

### 4.5 Application adapter contract

`discover_app`, `supported_modes`, `activate`, `deactivate`, `send_6dof`, `perform_command`, `query_command_list`, `health`, `permission_status`. Integrate natively where possible. App plugin actions must run in the host application's supported scripting/plugin interfaces, not private-memory hacks or fake universal key mappings.

### 4.6 Session and action routing policy

1. A native 6DOF application gets motion through **one** verified native integration route.
2. Global desktop actions activate only under a deliberately configured desktop profile or explicit mode switch; no accidental desktop scrolling while using CAD.
3. Buttons routed to native app commands may coexist with motion only if event ownership and button mapping are proven collision-free.
4. No input injection while locked, in secure authentication fields, or in unpermitted contexts.
5. When compositor capability is missing, mark command inactive and explain what is needed; never claim successful execution without feedback.

## 5. Configuration and data model

A schema-versioned profile should support:

```
Profile {
  schema_version: integer
  id: uuid
  display_name: string
  scope: {global | device | application | workspace}
  device_selector: optional stable device selector
  app_selector: optional application identity
  navigation: {
    translation_gain: float
    rotation_gain: float
    axis_map: six-axis transform
    per_axis_gain: six floats
    per_axis_invert: six booleans
    deadzone: six normalized nonnegative floats
    response_curve: {linear | power | s_curve}, parameters
    smoothing_time_ms: nonnegative float
    dominant_axis: boolean
    translation_enabled: boolean
    rotation_enabled: boolean
  }
  bindings: map<physical_button_id, action_definition>
  radial_menus: validated menu definitions
  osd: display preferences
  native_app_mode: enum
  modified_at: timestamp
}
```

Document exact units and ranges in schema and UI. Profile changes use transactions/atomic replace and support backup/restore. Unknown future fields should survive round-trip where safe. Never deserialize arbitrary code from imported profiles.

## 6. Nonfunctional requirements and SLOs

The following are **engineering targets**, not guarantees already met:

| Property | Acceptance target | Measurement |
|---|---|---|
| Device discovery | Ready within 2 seconds of enumeration under normal conditions | 100 hotplug tests/device |
| Input latency | p95 <= 15 ms, p99 <= 30 ms from user-space decoded input to output in local tests, excluding target app rendering and unavoidable Bluetooth link delay | Timestamp trace and hardware-appropriate benchmark |
| Idle resource usage | Baseline service < 1% CPU on reference x86_64 test host; UI not running has near-zero renderer overhead | 30-min idle test |
| Memory | Session service target < 100 MB RSS in default setup; measure each component separately | Instrumented soak |
| Recovery | Reconnect <= 5 sec after OS indicates device available, when the underlying transport cooperates | 100 reconnection cycles |
| Stability | 72-hour soak with no unhandled crash, stuck state, duplicate events, or unbounded memory increase | Repeated motion/disconnect/application switching |
| Installation | Fresh supported OS + package manager installation, no manual permission edits | VM + bare-metal matrix |
| Profiles | Atomic persistence; no lost data under forced process termination | Fault-injection tests |
| Security | No world-writable device permissions, shell-injection path, unintended network listener, or untrusted macro execution | Static + dynamic security suite |
| Accessibility | Keyboard-operable primary workflows, labels, contrast and screen-reader semantics evaluated | Accessibility test plan |

Avoid global latency assurances across USB and Bluetooth without hardware timestamps; explicitly document measurement boundaries.

## 7. Acceptance test suite and hardware lab

### 7.1 Automated

- Codec golden fixtures for every verified VID/PID, descriptor and firmware variant.
- Property-based tests: all axes finite and bounded; stable neutral; signs and mappings correct; disconnect resets outputs.
- Fuzz HID decoders, profile importer, IPC commands, browser bridge (if present).
- Unit/integration tests for per-axis filters, gain, deadzone, curves, smoothing, response to timestamp jumps, macro engine, priority rules.
- Multi-device test: separate IDs, profiles, active owner policy, duplicate event prevention.
- Simulated hotplug, disconnect during key down, service restart, suspend/resume, profile switch during motion, active app transitions, locked screen.
- Legacy interoperability: Blender/FreeCAD with spacenavd/libspnav; X11 native + AF_UNIX tested separately.
- Installer matrix: clean installation, user upgrade, rollback, partial install recovery, missing dependency, package conflict, uninstall with/without settings.
- Reproducible CI on Ubuntu/Debian/Fedora/Arch where feasible; test X11 and Wayland with software compositors but do not equate VM success with physical HID success.
- Security: permission audit, port audit, root/user privilege analysis, corrupted settings recovery, code signing verification, supply-chain scanning.

### 7.2 Physical validation (required for full support)

Each physical model/revision/transport must pass: enumerate, no spurious device matches, raw axes six directions plus combined motions, all physical buttons, profile changes, neutral/no-drift, battery/status if exposed, outputs if declared, reconnect, power cycle, suspend/resume, 2-hour sustained use, and native application integration. Store signed or reviewable test results, photos if licensed/consented, sanitized event recordings and test software versions. Track `tested`, `partially tested`, `not available`, and `blocked` separately.

**Hard gate:** Claimed support for all models cannot be accepted until physical hardware or validated equivalent regression evidence exists for each distinct model/revision/transport. Hardware unavailable -> honest partial status and a documented test plan, not fabricated success.

### 7.3 Application coverage

For each app/version/desktop: app discovery, active profile switch, all six axes, button mapping, whether camera/object navigation is native, view shortcuts if supported, lock screen, no duplicated motion, no regression with existing spacenavd. Publish matrix and known caveats. Include Blender, FreeCAD, KiCad, OpenSCAD, PrusaSlicer and a browser-based CAD case; test further applications by demand.

## 8. Threat model and safety controls

Potential attackers/risks: hostile profile import, malicious web origin sending commands, forged IPC client, unsafe udev permissions, permission escalation, untrusted device with malformed HID reports, virtual input sent to password dialogs, repeated/stuck keys, untrusted plugin packages, supply chain compromise, unauthorized telemetry.

Mitigations: authenticate IPC using Unix credentials; permission-bound session control; restrict privileged broker API; minimize ambient capabilities; validate all events/commands; enforce size/rate/recursion limits; default-off arbitrary shell macros and network bridges; no unsigned remote code installation; disable synthetic input in protected contexts where detectably possible; redact diagnostics; privacy-by-default; document limitations of compositor focus awareness.

## 9. Packaging details and reliability workflow

- Build packages in CI with dependency locks and SBOM; attach hashes and signing instructions.
- Service watchdog/restart/backoff; detect crash loops and present actionable GUI warnings.
- System service runs only as privileged as unavoidable, with `NoNewPrivileges`, device allowlisting and capability minimization where practical; test device access against hardening directives.
- Distinguish package upgrade of service binary from config schema migration; backups and backward-compatible revert where possible.

## 12. Project governance and verification contract

For every phase, Claude Code must output:

1. Evidence gathered and sources, including date and commit hash.
2. Decisions made (ADRs), assumptions, alternatives rejected, security impacts.
3. Files added/modified and minimal reason for each change.

No phase is complete solely because source code compiles. Require runnable behavior and automated tests. If hardware is absent, implement simulation and clearly designate physical validation as blocked. Prefer debugging root causes to superficial fallbacks. Do not suppress failing tests. Do not claim tests were executed if they were not.

## 13. Release gates and definition of done

**Alpha:** At least one physically tested device with complete basic motion/button path; installer on target Pop!_OS/Ubuntu environment; GUI calibration and diagnostics; no app interference; automated tests green; unsupported capability matrix visible.

**Beta:** Multiple distinct physically verified models/transports; app-aware settings; macros/buttons; Wayland desktop matrix; upgrades and rollback; 72-hour stability test; security review; documented incompatibilities.

**1.0 Stable:** Explicit published supported hardware/device revision matrix, including functional level by model; reproducible installation/upgrade/recovery; verified native application compatibility; robust profiles, GUI and diagnostics; release-quality accessibility and docs; no critical security or data loss bugs. **Do not call it universal full-feature parity until all advertised Enterprise/wireless/legacy requirements are physically validated.**
